Authentication

Identity is an email + password. Successful login or registration returns an opaque bearer token; every other request carries it in the Authorization header, and the owning user is derived from it - never from a client-supplied id.

The session model

Each login creates a row in the sessions table:

Token
32 random bytes, url-safe base64, handed to the client once.
Digest
The SHA-256 of the token is what is stored - a database leak exposes no usable sessions.
Expiry
Sessions expire after SESSION_TTL_DAYS (default 30).
Revocation
Logout revokes the current session; password change revokes every other session; account deletion removes all sessions.

Token lifecycle

  1. Register or login → AuthResponse with token + user.
  2. The SPA stores the token in localStorage (doctordrobe_token) and attaches it to every request.
  3. On startup the SPA re-hydrates the profile via GET /api/auth/me; a 401 clears the stored token and signs out.
  4. Logout best-effort revokes the token server-side, then clears local state.

Password handling

  • Hashed with pbkdf2_hmac (SHA-256, 260,000 iterations) and a per-user random salt - see app/utils/passwords.py.
  • Minimum length enforced by PASSWORD_MIN_LENGTH (default 8) at registration and change.
  • Emails are normalized to lowercase for uniqueness - registration with Test@Example.com and test@example.com conflicts.
  • Login failures return a uniform 401 ("Incorrect email or password") so attackers can't tell which part was wrong.

Login rate limiting

An in-memory per-IP limiter (per process) budgets AUTH_LOGIN_MAX_ATTEMPTS (10) attempts within AUTH_LOGIN_WINDOW_SECONDS (900 s). Beyond that, login returns 429. It honours X-Forwarded-For when present. This is best-effort on a single instance - a distributed limiter is a documented production upgrade.

Ownership, not just authentication

Every user-scoped endpoint resolves the owner from the token:

  • GET /api/checkups/{id} → 403 if the checkup belongs to another user.
  • POST /api/checkups takes no user id in the body at all.
  • DELETE /api/auth/me cascades to all checkups and sessions.

Why no user_id params?

The old API accepted user_id as a query param - trivially guessable and forgeable. The auth migration removed that surface entirely; tokens are the only identity the API trusts.

Roadmap

  • Password recovery - email-based reset; deliberately omitted for now (self-hosted project).
  • Passkeys / WebAuthn - a stronger credential than passwords.
  • Distributed rate limiting - Redis-backed limiter for multi-instance deploys.
  • Session list UI - see and revoke active sessions from Settings.
