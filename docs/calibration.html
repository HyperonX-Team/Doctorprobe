Calibration tutorial — make SaliNet real

SaliNet ships trained on simulated strip chemistry. This tutorial replaces that with real measurements: build control standards, collect labeled samples with the firmware's calibration mode, export, retrain, and verify.

What "real" means here

The goal is a per-analyte model trained on samples from your device and your strips, labeled by standards you made. That is the honest path to accuracy — and the only thing that makes the reported numbers defensible.

The workflow

  1. Build control standards with known concentrations.
  2. Arm the firmware (CAL <analyte> <concentration>), put a strip under the sensor, press the button — the device averages 10 reads and POSTs one labeled sample.
  3. Repeat across levels until every analyte has ≥ 15 samples.
  4. Export the training CSV and run the trainer.
  5. Verify against a known control; clear the samples.

1. Control standards

A control standard is a solution with a known analyte concentration. The analyzer's acceptance envelopes (from app/schemas/calibration.py):

AnalyteEnvelopeStandard recipe
Glucose0.05–50 mg/dLPure dextrose powder dissolved in distilled water (0.5 g in 1 L = 50 mg/dL; weigh on a 0.01 g scale). Use high-sensitivity glucose strips.
CRP0.005–20 ng/mLCommercial immunoassay control kits or lab-prepared standards — home chemistry is unreliable here; plan a lab session.
Cortisol0.005–5 µg/dLCommercial ELISA-type control kits or lab-prepared standards.
sIgA0.5–200 mg/dLCommercial IgA standards or lab-prepared dilutions.
pH—Never calibrated. pH is a mixed-indicator ratio (closed-form channel ratio).

Strategy: cover at least 5 concentration levels per analyte, spanning the physiological reference range, with ≥ 15 samples per level. More spread beats more replicates of the same value.

2. Capture samples

From the serial monitor at 115200 baud:

CAL glucose 2.5      # arm: label the NEXT capture
# ...place the control strip under the sensor and press the button...
# the device averages 10 readings and posts one labeled sample

CAL glucose 5.0      # next level
CALCLEAR             # disarm without capturing

Watch the app's Calibration page (or GET /api/calibration/stats) to see counts climb per analyte.

3. Export and retrain

# From the app: Calibration → Export training CSV (or:)
curl -o backend/data/real_training.csv http://localhost:8000/api/calibration/export

cd backend
python scripts/generate_synthetic_data.py   # fallback for uncalibrated analytes
python scripts/train_model.py

The trainer's data priority:

  1. Real data — an analyte uses its real samples when it has ≥ 15 (the MIN_REAL_SAMPLES threshold, shown in the dashboard).
  2. Synthetic fallback — analytes below the threshold keep the simulated dataset so the model stays complete.

Output: app/services/model/salinet.joblib (one forest per analyte) and salinet.json, the manifest recording trained_at, per-analyte provenance (real vs synthetic, sample counts) and held-out metrics (R², MAE).

4. Verify

  • Run a checkup on a known control standard; the reported value should match the label within the model's MAE.
  • Confirm the manifest now says "source": "real" for the calibrated analytes (Calibration page shows this per analyte).
  • Spot-check the extremes: a blank strip should read near the bottom of the range; a strong standard near the top.

5. Clear

curl -X DELETE http://localhost:8000/api/calibration/samples
# or: Calibration → Clear samples

The calibration dashboard

The app's Calibration page answers the two questions that matter:

  • Coverage — per-analyte sample count vs the 15-sample threshold, concentration span, and a "Ready to train / Keep collecting" badge.
  • Model status — version, training timestamp, and per-analyte data source (real vs synthetic) straight from the manifest.

Why one forest per analyte?

Control samples are labeled per analyte, so per-analyte forests fit the data collection naturally — and each forest's feature importances show exactly which sensor channel drives that analyte. See analysis science.
