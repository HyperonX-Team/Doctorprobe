Deployment

The stack is designed to be run with Docker Compose today and graduated to a managed setup tomorrow — same images, env-driven configuration throughout.

Docker Compose

cp .env.example .env      # set FERNET_KEY, DEVICE_API_KEY
docker compose -f infra/docker-compose.yml up --build

What happens at startup:

  1. postgres starts and becomes healthy (pg_isready).
  2. backend waits for postgres, runs alembic upgrade head, then serves uvicorn on 8000 (healthchecked via curl /health).
  3. frontend waits for the backend and serves the SPA via Nginx on port 80, proxying /api/* to the backend (healthchecked via wget /health).

The backend container runs as an unprivileged user (defense in depth), and images are built from slim base images.

The Nginx proxy

  • Serves the static SPA (built by the multi-stage frontend image).
  • Proxies /api/* → backend:8000, so the browser talks to one origin (no CORS in production).
  • The frontend's production build points VITE_API_BASE_URL at /api.

TLS

Terminate HTTPS at a reverse proxy (Caddy, Nginx, Traefik, or a load balancer) in front of the stack:

  • Forward X-Forwarded-For / X-Forwarded-Proto (the app honours them).
  • Restrict CORS_ORIGINS to the real origin(s).
  • Set USE_HTTPS true in the firmware and point it at the TLS endpoint (NTP sync + trust bundle required).

Secrets

  • Inject FERNET_KEY and DEVICE_API_KEY via the orchestrator's secret store (Kubernetes Secrets, Docker secrets, Vault) — never bake them into images.
  • Never commit .env or the firmware's secrets.h.
  • Generate FERNET_KEY with python -c "import secrets; print(secrets.token_urlsafe(48))".

Database

  • PostgreSQL 16 in production (asyncpg driver); SQLite for local dev.
  • Enable volume backups and consider a managed instance for HA.
  • Migrations run automatically at container start; for blue/green deploys, run alembic upgrade head as a separate step first.

Observability

  • The backend emits structured JSON logs (request id, method, path, status, duration) to stdout.
  • /health supports orchestrator probes.
  • Aggregate logs with your collector; alert on 5xx spikes and login rate-limit hits.

Scaling & hardening notes

  • Multi-instance backend — the login rate limiter is per-process; move it to Redis before scaling horizontally.
  • Device fleet — today devices share one DEVICE_API_KEY; per-device keys with rotation and a device registry are the documented next step (the dependency seam in app/core/security.py is where they plug in).
  • Key rotation — rotating FERNET_KEY requires re-encrypting stored reports; plan a migration job or use a KMS.

Production checklist

  1. Real FERNET_KEY in the secret store.
  2. DEVICE_API_KEY set and mirrored in firmware secrets.h.
  3. CORS_ORIGINS restricted to the real origin.
  4. TLS terminated; firmware USE_HTTPS true.
  5. PostgreSQL with backups; migrations as a deploy step.
  6. Health checks wired into the orchestrator.
