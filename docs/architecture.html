Architecture

Three independent layers - device, API, and browser - joined by HTTP, with every biomarker report encrypted at rest.

The layers

1. Device (ESP32 firmware)

The physical layer. A TCS34725 RGB colour sensor reads a saliva strip; a DHT22 records ambient temperature and humidity. On button press, the firmware normalizes each RGB channel against the sensor's clear channel (making readings lighting-independent) and POSTs a snapshot to /api/devices/reading, optionally protected by an X-API-Key header.

2. Backend (FastAPI)

The intelligence layer. It authenticates browser sessions, ingests device readings, runs the biomarker analysis, encrypts reports, and serves trends. The analysis pipeline (app/services/) is deterministic: the same snapshot and profile always produce the same report.

3. Database (SQLAlchemy + Alembic)

PostgreSQL in production, SQLite for development. Migrations are managed with Alembic and run automatically at container start. Report payloads are stored encrypted with Fernet; only a plain summary and risk label stay readable for list views.

4. Frontend (React SPA)

The presentation layer. A chat-style UI for reports, a trends page with SVG charts, a vault for exports, and a calibration dashboard. All requests carry the session bearer token; ownership is enforced server-side.

Anatomy of a checkup

  1. Capture. The user presses the device button; the firmware posts one or more snapshots (a burst) of the same strip.
  2. Ingest. POST /api/devices/reading (or /readings for bursts) stores raw snapshots.
  3. Analyse. POST /api/checkups loads the newest burst for the user's device, applies the blank-pad baseline correction if one exists, and runs the spectral solver with the SaliNet prior.
  4. Encrypt. The full report is serialized, encrypted with Fernet, and stored with a plain summary, risk label, and quality grade.
  5. Present. GET /api/checkups/{id} decrypts and returns the report; the SPA renders it, grades the measurement, and offers sharing, saving, and PDF export.

Two trust domains

The API deliberately separates device identity from user identity:

  • Devices authenticate with a shared X-API-Key header on ingest endpoints (enforced when DEVICE_API_KEY is set). Constant-time comparison prevents timing attacks.
  • Browsers authenticate with opaque bearer tokens issued by /api/auth. The owning user is always derived from the token - endpoints never accept a client-supplied user id.
